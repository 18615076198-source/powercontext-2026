# 技术说明

## 1. 总体结构

~~~text
Dify Chatflow（编排）
  start ──> if-else（查档案？）
              ├─ true  ──> HTTP /api/history ──> LLM 档案管理员 ──> answer
              └─ false ──> HTTP /api/match ──> LLM 月老 ──> HTTP /api/archive ──> answer
                                │                                   │
                                ▼                                   ▼
                      seekdb personas（混合检索）           seekdb matches（记忆）
                                ▲
                     本地 bge-small-zh INT8 embedding（Node 侧）
~~~

- **Dify 负责**：意图分支、调用外部服务、模型生成、把结果返回给用户；
- **配套后端负责**：本地向量化、seekdb 读写、把检索结果整理成 LLM 可引用的事实；
- **seekdb 负责**：候选人的向量 + 全文混合检索，以及跨会话的相亲档案。

## 2. seekdb 数据设计

| collection | 内容 | 索引 |
| --- | --- | --- |
| `personas` | 24 位角色的档案（姓名、年龄、城市、职业、tags、redflags、口头禅、小传），id = `p01…p24` | `VECTOR(512) HNSW cosine` + `FULLTEXT(ik, smart)` |
| `matches` | 每次相亲：用户、简历、候选人、月老批语、时间 | 同样 512 维向量索引（用于后续相似档案），元数据过滤 `user` |

- 写入：`collection.upsert` + `refresh_index()`，保证新档案立即可查；
- 记忆读取：`collection.get({ where: { user }, limit: 5 })`，按 user_id 隔离；
- 撮合检索：一次 `collection.hybridSearch`：

~~~js
await collection.hybridSearch({
  query: { whereDocument: { $contains: 命中标签 } },   // 全文一路
  knn: { queryEmbeddings: [简历向量], nResults: 8 },   // 向量一路
  rank: { rrf: { rankWindowSize: 60, rankConstant: 60 } },
  nResults: 8,
  include: ["documents", "metadatas", "distances"],
});
~~~

融合与排序由 seekdb 在库内完成（`DBMS_HYBRID_SEARCH` + RRF），客户端只接收最终结果。

## 3. 为什么这样设计

1. **向量 + 全文缺一不可**：简历里既有「猫、手冲咖啡」这种关键词，也有「想找个能一起安静待着的人」这种语义；
   混合检索让「关键词命中」和「语义相近」都能进入候选，再由 RRF 融合。
2. **记忆是玩法的一部分**：题面要求角色/剧情/历史能被复用。月老记住「上次为什么黄了」，
   才有连续剧感；seekdb 的 `matches` 就是这个记忆库。
3. **embedding 放后端而不是 Dify**：Dify 的知识库需要额外向量库与索引流程；本题只需要 24 位角色 + 档案，
   用独立 collection 更轻，也避免把「Dify 的 embedding」和「seekdb 的检索」拆成两套。
4. **raw-text 协议**：Dify HTTP 节点的 JSON body 是字符串模板，LLM 输出里的换行/引号会破坏 JSON；
   改成人可读的 `KEY=value` 文本块，后端按行解析，稳定且好调试。

## 4. 检索质量与调参

- 标签抽取：从简历/聊天里匹配 90 个预置标签（猫、咖啡、看展、剧本杀…），取第一个命中作为全文查询词；
  没有命中时退化为纯向量检索（返回 `mode: "vector"` 便于观察）；
- 候选数：取 `nResults = max(6, topK*2)`，再按历史排除已见过的人，最后截断 3 位；
- 经验：`rankWindowSize=60` 时，关键词强匹配的人排在前列，语义相近但标签不同的人作为补充；
- 后续可加：把用户的「雷点」做成负向标签做 where 过滤，或对候选做一次 LLM 精排。

## 5. 工程细节

| 问题 | 处理 |
| --- | --- |
| 角色池初始化 | 后端启动时若 `personas` 为空则自动 seed；`POST /api/seed` 可重建 |
| 重复写入 | `matches` 用时间戳 id，天然追加；`personas` 用固定 id + seed 重建 |
| 索引可见性 | 写后调用 `refresh_index()`，自测里验证过「写完立刻能查到」 |
| 请求解析 | JSON 与 raw-text 双协议，`parseBlocks` 按 `KEY=` 行解析，报告块保留换行 |
| 候选人识别 | 归档时从报告中反向匹配角色名，避免让 LLM 输出结构化字段 |
| 失败降级 | 混合检索异常时自动退化为向量检索；LLM 未配置时本地执行器用模板输出并标注 |

## 6. 与题面要求的对应

| 题面要求 | 本项目 |
| --- | --- |
| 必须使用 Dify | Chatflow DSL，6 类节点、意图分支、两次 HTTP、两次 LLM |
| 实际使用 seekdb | 混合检索 + 记忆存储，两条职责都在应用主流程里 |
| 可体验 | Dify 对话界面直接玩；无 Dify 时用本地执行器验证接线 |
| 可复现 | 24 位角色数据、模型、seed 脚本、验证样例、运行日志都在仓库里 |
