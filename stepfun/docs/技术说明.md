# 技术说明（一页）

> 端侧 AI 推理性能优化与 seekdb 混合检索 · 迷你知识库
> 仓库 `18615076198-source/powercontext-2026` · 分支 `2026-competition-stepfun` · 目录 `stepfun/`

## 1. 模型与量化

| 项 | 内容 |
| --- | --- |
| 模型 | `Xenova/bge-small-zh-v1.5`（BAAI bge-small-zh-v1.5 的 ONNX 转换，MIT，512 维，24M 参数） |
| 运行时 | Transformers.js 4.3.2 + ONNX Runtime Web 1.31（esbuild 打包，本地静态加载） |
| 获取方式 | `npm run fetch-model` 固定版本从 hf-mirror 下载，校验文件级体积（见 `manifest.json`） |
| 量化方案 | INT8 动态量化（`model_quantized.onnx`）与 FP16（`model_fp16.onnx`），与 FP32 基线对比 |
| 体积 | FP32 90.46 MB → FP16 45.30 MB（2.00×）→ INT8 22.90 MB（**3.95×**） |
| 质量 | 12 条查询 Recall@5：FP32/FP16 0.9028 → INT8 0.8611（相对 −4.6%）；nDCG@10：0.8582 → 0.8341（相对 −2.8%） |

量化前后用同一套语料、同一批查询、同一评测口径（Recall@5、nDCG@10，标注见 `data/eval.json`），
INT8 的下降集中在个别多相关文档的查询上，没有出现灾难性退化；因此默认使用 INT8。

## 2. 端侧运行与后端选择

- **推理位置**：文档向量化与查询向量化都在浏览器内完成；服务端只接收向量，不接收原文做推理，也不调用任何云端 API。
- **WebGPU 选择**：页面启动时调用 `navigator.gpu.requestAdapter()`；拿到 adapter 时显式使用 `device: "webgpu"`，
  并自动选择 FP16；拿不到时使用 `device: "wasm"` + INT8。
- **自动降级**：WebGPU 管线初始化抛错会捕获并重建 WASM 管线，界面顶部徽标与状态行展示实际后端与降级原因；
  无头浏览器（拿不到 adapter）与普通浏览器（可用 WebGPU）两条路径都实测过：
  - 无头 Edge 156：`requestAdapter() 返回 null` → 自动 WASM，检索流程正常；
  - 有界面 Edge 156：adapter 可用 → WebGPU 生效，页面徽标显示 WebGPU。
- **多线程 WASM**：服务端返回 `Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy`，开启跨源隔离，
  使 SharedArrayBuffer 与 ORT wasm 多线程可用。

## 3. seekdb 存储与混合检索

**集合结构**（每个会话一个 collection，名如 `kb_<sessionId>`）：

| 部分 | 配置 |
| --- | --- |
| 向量列 | `VectorIndexConfig({ hnsw: { dimension: 512, distance: "cosine" } })` |
| 全文索引 | `FulltextIndexConfig("ik", { ik_mode: "smart" })` |
| 文档/元数据 | 原文 `documents` + JSON 元数据（`docId/title/category/chunk`） |
| 主键 | `docId#chunkIndex`，写入用 `upsert` 保证幂等 |

**混合检索**：查询向量由浏览器计算后传入，服务端调用一次

~~~js
await collection.hybridSearch({
  query: { whereDocument: { $contains: query } },   // 全文一路
  knn:   { queryEmbeddings: [embedding], nResults: k }, // 向量一路
  rank:  { rrf: { rankWindowSize: 60, rankConstant: 60 } },
  nResults: k,
});
~~~

底层由 seekdb 的 `DBMS_HYBRID_SEARCH` 在库内完成两路召回与 RRF 融合，**客户端不分别取两路结果再拼合**；
返回的 `mode` 字段会标明本次是 `hybrid` 还是降级后的 `vector`。

**增量写入与刷新**：导入时只写新增文档；写入完成后调用 `refresh_index()`，
让新文档立即可检索（自测脚本专门验证：增量导入后立即检索能命中新文档）。刷新耗时单独统计。

## 4. 状态管理与性能优化

- **会话/集合状态**：浏览器 localStorage 保存 sessionId，服务端按 sessionId 映射 collection；
  服务重启后按集合名重新挂载；「清空知识库」删除并重建当前会话的 collection，不影响其他会话。
- **向量化批处理**：默认 batch=8（可调 1–32），减少 JS↔WASM/GPU 往返；UI 实时显示进度与每批耗时。
- **写入批处理**：单次请求携带整批块，服务端按 32 条一批 `upsert`，避免逐条写放大。
- **索引刷新策略**：一次导入只刷新一次，而不是每条都刷新（刷新约 0.3–0.7 s / 40 块）。
- **检索链路**：查询向量化 + 一次 hybridSearch，无客户端 rerank、无二次查询。

**关键对比**（同一设备/浏览器/语料/查询，详见 `docs/benchmark.md`）：

| 配置 | 体积 | 向量化 40 块 | p50 查询延迟 | Recall@5 |
| --- | ---: | ---: | ---: | ---: |
| INT8 + WASM | 22.90 MB | 703 ms | **11.9 ms** | 0.8611 |
| FP16 + WASM | 45.30 MB | 1469 ms | 15.2 ms | 0.9028 |
| FP32 + WASM | 90.46 MB | 1292 ms | 19.2 ms | 0.9028 |
| FP16 + WebGPU | 45.30 MB | 894 ms | 61.6 ms | 0.9028 |

结论：INT8 把体积压到 1/3.95、加载与向量化最快、质量仅小幅下降；小模型单查询场景 WASM 更快，
WebGPU 在批量导入时吞吐接近或略优。产品默认仍是 WebGPU 优先（符合题面要求），同时提供手动切换。

## 5. 复现

~~~bash
npm install
bash scripts/start-seekdb.sh     # 或使用已有 seekdb（127.0.0.1:2881）
npm start                        # http://127.0.0.1:7860
npm run selftest                 # 无头浏览器 8 项断言
node scripts/benchmark.mjs --dtypes q8,fp16,fp32 --device wasm
~~~

测试环境：Windows 11 · Intel Core Ultra 9 275HX · RTX 5070 Ti Laptop + Intel iGPU ·
Edge 156.0.4314.58 · Node 24.21.0 · seekdb 1.4.0（WSL2，127.0.0.1:2881）。

## 6. 后续改进

1. 模型改用领域微调的小模型或更小的 q4 量化，进一步降低首屏；
2. 查询侧引入查询改写/多路召回，抵消 INT8 带来的少量质量损失；
3. WebGPU 侧尝试 IO binding / 图捕获，降低逐次调度开销；
4. 增加图片等多模态扩展（题面允许的加分项）。
